# 운영 런북: 24시간 이상 소크(soak) 테스트 시나리오

> **이 문서는 시나리오 정의(definition)만 다룬다.** 실제 실행은 Linux + 실
> NVIDIA GPU(CUDA 프로파일) 호스트가 필요하며, 그 실행은 issue #128
> (실 Linux+CUDA 호스트 QA 라운드)로 넘긴다. 이 문서 작성 시점에는 소크
> 테스트를 실행하지 않았고, 결과 기록도 없다 (#129).

## 배경

지금까지 관찰된 최장 연속 실행 시간은 수십 분 단위다. 요양원 배포는 카메라가
24시간 365일 끊김 없이 돌아야 하는 환경이지만, 다음과 같은 실패 모드는 짧은
관찰 창으로는 드러나지 않는다.

- 메모리/파일디스크립터 누수
- RTSP 재연결이 누적되며 발생하는 열화
- clip 디스크 회전(rotation)이 여러 사이클에 걸쳐서도 올바르게 동작하는지
- 장시간 fps 안정성

clip recorder는 부팅 시 **1회** sweep/rotate/admit 순서로 실행되도록
보장되어 있을 뿐 (`worker/runtime/worker.py:1170-1177`,
`_compose_evidence_export`의 docstring 및 `ClipRecorder.start()` 경로 — 이
순서는 `tests/test_evidence_export_startup.py`가 계약으로 고정), 이 로직이
장시간 실행 중 반복적으로 올바르게 동작하는지는 코드만으로는 보장되지 않는다.
또한 clip evidence의 핵심 내구성 경로가 `/proc/self/fd/{descriptor}`
(`worker/pipeline/output/evidence/evidence_media.py:75`)에 의존하는 **Linux
전용** 구현이라, fd 누수 관찰 자체도 Linux 호스트에서만 유효하다.

## 시나리오 정의

| 항목 | 값 |
| --- | --- |
| 실행 시간 | 24시간 이상 연속 |
| 카메라 수 | 2개 이상 RTSP 카메라 |
| clip 저장 | `clip.enabled=true` (worker YAML 또는 env — [`docs/operations/config-pitfalls.md`](config-pitfalls.md) #3 참고) |
| 이벤트 주입 | 낙상/침대이탈 이벤트를 주기적으로 인위 발생 (예: 사람이 직접 시연하거나 테스트 클립 재생) |
| 실행 환경 | Linux + 실 NVIDIA GPU 호스트 (CUDA 프로파일). macOS/MPS 환경은 `/proc/self/fd` 부재로 clip 경로의 본래 코드가 실행되지 않아 대상 아님 |

## 측정 지표와 통과/실패 기준

### 1. 메모리(RSS) 증가 추이

- **측정**: worker 프로세스 RSS를 일정 주기(예: 5분)로 샘플링해 시계열로
  기록한다 (`ps -o rss= -p <pid>` 또는 `/proc/<pid>/status`의 `VmRSS`).
- **기준**: 24시간 구간에 선형 회귀(slope)를 적합해 시간당 증가율을 구한다.
  - **통과**: 24시간 동안 RSS 증가율이 **시간당 1% 미만**(테스트 시작 시점
    RSS 대비)이고, 증가 패턴이 선형이 아니라 초기 워밍업 후 평평(plateau)한
    형태를 보인다.
  - **실패**: 24시간 동안 지속적으로 선형 증가하거나, 시간당 1% 이상의
    증가율이 관찰되면 누수로 간주하고 별도 버그로 분리한다.
  - 절대 임계값이 아닌 추세(slope) 기준으로 판단하는 이유: 카메라 수/해상도에
    따라 절대 RSS는 배포마다 다르지만, 시간에 따라 우상향하는 추세는 배포
    조건과 무관하게 누수 신호이기 때문이다.

### 2. 파일 디스크립터(fd) 카운트 안정성

- **측정**: `/proc/<pid>/fd`(worker PID) 내 항목 수를 RSS와 동일한 주기로
  샘플링한다. clip evidence 경로가 `/proc/self/fd/{descriptor}`를 직접
  사용하므로(`worker/pipeline/output/evidence/evidence_media.py:75`) 이
  경로는 **Linux 전용**이며, 이 지표 역시 Linux 호스트에서만 유효하다.
- **기준**:
  - **통과**: fd 카운트가 이벤트/재연결 발생과 상관없이 일정 범위 내에서
    등락하며, 24시간 구간 전체에서 우상향 추세가 없다.
  - **실패**: 이벤트 주입 또는 RTSP 재연결 이후 fd 카운트가 회복되지 않고
    누적 증가하면 누수로 간주한다.

### 3. RTSP 재연결 횟수 및 복구 시간

- **측정**: 네트워크 차단 등으로 RTSP 연결 끊김을 인위적으로 유발하고, 로그에서
  재연결 이벤트 발생 시각과 스트림 정상화(프레임 재수신) 시각을 추출한다.
- **기준**:
  - **통과**: 재연결이 매번 성공하고, 복구 시간이 테스트 전체에서 일정 범위
    (초기 재연결과 24시간 후 재연결 간 유의미한 지연 증가 없음)를 유지한다.
  - **실패**: 재연결 누적에 따라 복구 시간이 점점 길어지거나, 재연결이 실패해
    카메라가 영구적으로 죽은 상태로 남으면 실패로 기록한다.

### 4. 장시간 라이브뷰 fps 안정성

- **측정**: 테스트 시작 시점과 24시간 후 시점의 measured fps를 비교한다
  (`/status` 엔드포인트의 `runtime.cameras[*]`, `runtime.device` 등 폴링 —
  아래 절차 참고).
- **기준**:
  - **통과**: 시작 시점과 24시간 후 시점의 measured fps 차이가 설정된
    목표 fps(`ML_DEFAULT_CAMERA_FPS` 또는 worker 기본값 5.0) 대비 10% 이내다.
  - **실패**: fps가 지속적으로 하락하는 추세를 보이거나 10%를 초과해
    저하되면 실패로 기록한다.

### 5. clip 디스크 회전(rotation) 정확성 — 반복 사이클

- **측정**: clip 저장이 디스크 공간 상한에 가까워지도록 유도(또는 충분히 긴
  시간 동안 자연 누적)한 뒤, 오래된 clip이 정책대로 삭제되는지 여러 사이클에
  걸쳐 확인한다. `ClipRecorder.start()`의 sweep/rotate/admit 순서는 **부팅
  시 1회**만 보장되므로 (`worker/runtime/worker.py:1170-1177`), 소크 테스트의
  목적은 재부팅 없이 장시간 실행 중에도 이 회전 로직 자체(주기적 sweep 등)가
  반복적으로 올바르게 동작하는지 확인하는 데 있다.
- **기준**:
  - **통과**: 여러 회전 사이클에 걸쳐 디스크 사용량이 설정된 상한을 넘지
    않고, 오래된 clip이 정책대로(예: 오래된 순) 삭제된다.
  - **실패**: 회전이 멈추거나, 디스크 사용량이 상한을 넘어 지속 증가하거나,
    삭제 순서가 정책과 어긋나면 실패로 기록한다.

### 6. clip 카탈로그 무결성

- **측정**: 저장된 clip 파일과 카탈로그(메타데이터) 항목 수가 일치하는지,
  카탈로그에 있는 항목이 실제 파일을 가리키는지(orphan/dangling 참조 없음),
  주입한 이벤트 수와 카탈로그에 등록된 clip 수가 대응하는지 확인한다.
- **기준**:
  - **통과**: 카탈로그와 파일시스템 상태가 항상 일치하고, orphan 항목이나
    누락된 파일이 없다.
  - **실패**: 카탈로그에는 있으나 파일이 없는 항목, 또는 파일은 있으나
    카탈로그에 없는 항목이 발견되면 실패로 기록한다.

## 실행 절차

1. **환경 준비**: Linux + CUDA 프로파일 호스트에 2개 이상의 RTSP 카메라를
   연결하고, worker 설정에서 `clip.enabled=true`를 명시적으로 켠다 (YAML에서
   명시해야 승리한다 — [`config-pitfalls.md`](config-pitfalls.md) #3).
2. **베이스라인 기록**: 시작 시점의 worker PID, RSS, fd 카운트, `/status`
   응답(특히 `runtime.cameras`, `runtime.device`, `runtime.clip_recorder`)을
   기록한다.
3. **모니터링 시작**: RSS/fd 카운트를 일정 주기(예: 5분)로 CSV에 append하는
   스크립트를 백그라운드로 돌린다 (예: `ps`/`/proc` 파싱 + cron 또는 루프).
   동시에 backend `/status` 엔드포인트를 동일 주기로 폴링해 fps, clip_recorder
   진단 필드를 별도 CSV/로그로 남긴다.
4. **이벤트 주입**: 낙상/침대이탈 이벤트를 주기적으로 인위 발생시키고, 발생
   시각과 예상 clip 저장 여부를 별도로 기록한다.
5. **RTSP 장애 주입**: 최소 1회 이상 네트워크 차단으로 RTSP 연결을 강제
   끊고, 재연결 로그를 캡처한다 (끊은 시각, 재연결 감지 시각, 정상 프레임
   재수신 시각).
6. **24시간 경과 후 스냅샷**: 시작 시점과 동일한 방식으로 RSS, fd 카운트,
   `/status` 응답을 다시 기록한다.
7. **사후 분석**: 위 6개 지표 각각에 대해 통과/실패를 판정한다 (RSS/fd는
   시계열 CSV에 대해 추세 분석, fps는 시작/종료 시점 비교, clip 회전/카탈로그는
   파일시스템 + 카탈로그 대조).
8. **결과 기록**: 각 지표의 그래프(또는 원본 CSV) + 판정 결과를 정리해 이
   테스트를 실행한 QA 세션(issue #128)에 남긴다.
9. **버그 분리**: 어느 지표든 실패로 판정되면, 그 실패를 이 문서가 아니라
   재현 정보(설정, 시각, 로그 발췌)를 포함한 **별도 버그 이슈**로 분리해
   등록한다. 이 문서는 시나리오 정의이지 버그 트래커가 아니다.

### 캡처해야 할 것

- worker/backend 로그 전체 (특히 재연결, 에러, warning 레벨).
- RSS/fd 시계열 CSV.
- `/status` 폴링 결과 CSV (또는 JSON lines) — `runtime.cameras[*].fps`,
  `runtime.device`, `runtime.clip_recorder` 필드 위주.
- clip 저장 디렉토리의 파일 목록 + 카탈로그 덤프 (시작 시점, 종료 시점, 그리고
  최소 1회 중간 시점).
- 인위 주입한 이벤트/장애의 시각표 (사람이 직접 작성).

## 실행 주기 권장

- **릴리스 전(pre-release)**: worker의 clip recorder, RTSP 재연결, 라이브뷰
  경로에 영향을 주는 변경이 있었던 릴리스 직전에 최소 1회 실행.
- **정기(periodic)**: 그런 변경이 없더라도 회귀 확인을 위해 분기 1회 정도
  주기적으로 실행할 것을 권장한다. 정확한 주기는 #128 QA 라운드 이후 실제
  소요 시간과 리소스를 반영해 재조정한다.
- 소크 테스트가 CI에 편입될 수 있는지는 실 카메라/실 GPU 호스트가 필요하다는
  제약 때문에 별도 결정이 필요하다 (이 문서 작성 시점 기준 미결정 — #129
  수용 기준 항목 참고).
